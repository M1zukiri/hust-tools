# ncm2music.py 畸形/损坏 ncm 文件健壮性测试报告（黑盒）

- 被测对象：`D:\projects\网易云格式转换\ncm2music.py`（纯黑盒，未查看源码）
- 环境：Windows，Python 3.14.7
- 测试方式：fuzz 风格边界测试，每条用例 60 秒超时，挂起记为严重缺陷
- 样本说明：目录中原 93MB 真实样本已被移走，经确认后**按公开 ncm 格式规范自行加密构造合法样本**
  （AES-128-ECB + 密钥流异或，构造器 `make_ncm.py`），并保留加密前明文作为字节级 ground-truth。
- 基线验证：构造的 good_flac.ncm(4MB)/good_mp3.ncm(512KB)/small300.ncm(300B)/with_cover.ncm 均被工具
  正确转换，输出与明文**逐字节一致**（fLaC→.flac，ID3→.mp3）；0 字节音频样本被优雅拒绝（"解密结果为空"）。
  证明构造样本格式合法，后续畸形测试结论可信。

## 二、缺陷清单（按严重程度排序）

### D1（中）截断/不完整 ncm 文件被静默报"转换成功"，产出残缺音频且无警告
- 复现：取任一合法 ncm（如按公开规范自构的 4MB FLAC 样本），截断到 1KB / 1MB / 50% / 99%，
  执行 `python ncm2music.py truncated.ncm`。
- 实际：退出码 0，输出"OK -> xxx.flac"，产出文件头部是合法 fLaC 但内容缺失（1KB 截断仅产出 579 字节）。
- 影响：用户下载中断/磁盘错误造成的残缺文件会被当成"成功转换"，得到播放中途断掉的歌曲，无任何提示。
- 建议：转换前校验"头部声明的各块长度之和 ≤ 文件实际大小"；或至少校验文件尾非空音频。

### D2（中）文件内 CRC32 校验字段被完全忽略
- 复现：构造合法 ncm 但把 4 字节 CRC 字段写成错误值（生成脚本中 `build_ncm(..., corrupt_crc=True)`），转换。
- 实际：退出码 0 报"成功"，输出与明文逐字节一致。
- 影响：格式自带的完整性校验机制形同虚设，是 D1 与"音频区污染静默通过（C22）"的共同根因。
- 建议：对音频数据做 CRC32 校验，不匹配时给出警告或拒绝。

### D3（中）封面长度字段无边界校验，夸大值导致音频错位解密成垃圾仍报"成功"
- 复现：合法 ncm 的封面长度字段改为 100000（实际后接音频），转换。
- 实际：工具把音频前 100000 字节当封面跳过，剩余字节从密钥流起点错位解密为纯垃圾
  （头部 ef49b7c7），却因"垃圾不像 fLaC"被错标扩展名 .mp3，退出码 0 报"成功"。
- 影响：又一个静默数据损坏路径；且暴露了"扩展名靠解密后内容嗅探、内容全错时默认 mp3"的连锁问题。
- 建议：校验 coverlen ≤ 剩余文件大小；解密结果头部不识别（非 fLaC/ID3/0xFFEx）时应告警。

### D4（低）报错信息直接暴露内部异常原文
- 复现：C05/C06（`python ncm2music.py magic8.ncm`）等。
- 实际：用户看到 "unpack requires a buffer of 4 bytes"、"list index out of range" 等 Python 内部异常文本。
- 影响：可用性/观感问题；不泄露敏感路径，无安全风险。
- 建议：统一包装为"文件损坏/格式不支持"类用户可读提示。

### 观察项（非缺陷）
- O1：长度字段 0xFFFFFFFF 等极端值用例耗时约 1 秒（疑似整文件读入内存），未挂起未爆内存；建议仍加上限校验。
- O2：元数据长度为 0 时工具容错为"无元数据"，用源文件名命名并正确解密（C12），行为合理但无任何提示。
- O3：退出码语义清晰一致（全成功=0，任一失败=1）；批量模式坏文件隔离良好，不影响好文件（C32）。

## 三、总体评价

**可用性/健壮性（防挂起、防崩溃、防爆内存）：优秀。** 33 条畸形用例（含空文件、巨大长度字段、
随机垃圾、伪装扩展名、头部/元数据污染）全部在约 0.1~1.3 秒内优雅返回，退出码语义正确，
无一挂起、崩溃或内存失控；批量模式下坏文件完全隔离。

**数据完整性校验：薄弱（主要短板）。** 工具只解密、不校验：CRC 字段被忽略（D2），截断文件（D1）
和封面长度错位（D3）都会被静默报"成功"，用户无法察觉输出是残缺的。建议优先修复 D1/D2
（成本极低：一次 CRC32 校验 + 长度边界检查即可覆盖三个中危缺陷）。
